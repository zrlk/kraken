# Litmus suite for the WeakCore lowering table

Not from herdtools7. Written for Kraken to check that every instruction in
the WeakCore lowering table behaves on Kraken's Promising machine as herd7
says (or as the hardware manuals say, where herd has no model), in the
combinations lowered programs use. A model stricter
than herd or the hardware is a bug.

| core | x64 | AArch64 (`isaLSE2`) |
|---|---|---|
| `load` / `load acq` | `mov` / `mov` | `ldr` / `ldar`, `ldapr` (RCpc) |
| `store` / `store rel` | `mov` / `mov` | `str` / `stlr` |
| `cas` plain / acq / rel / acq rel | `lock cmpxchg` | `cas` / `casa` / `casl` / `casal` |
| `fence st` / `fence full` | nothing / `mfence` | `dmb ishst` / `dmb ish` |
| `casPair`, pair `ldp`/`stp` | `cmpxchg16b`, aligned 16-byte `mov` (`movdqa`) | `casp*`, LSE2 `ldp`/`stp` |

Which Kraken event each row is: `Kraken/Promising/Lower/EventsA64.lean` and
`EventsX64.lean`.

## Running

    lake build krakenlitmus_aarch64 krakenlitmus_x64
    python3 Kraken/Litmus/litmus_tests.py Kraken/Litmus/corpus/lowering/aarch64
    python3 Kraken/Litmus/litmus_tests.py --lse2 Kraken/Litmus/corpus/lowering/aarch64/lse2
    python3 Kraken/Litmus/litmus_tests.py --isa x64 Kraken/Litmus/corpus/lowering/x64

Expected: 159/0/0, 12/0/0 and 43/0/0 (match/mismatch/unsupported). Together
they take about 10 s; every test takes under 0.2 s and under 80 MB, so there
is no `slow.txt`. The two `open/` directories are outside the regression run
(see below).

## Layout and oracles

- **`aarch64/`** (159 tests, herd 7.58 oracles `.litmus.herd`).
  - 125 tests are generated by [gen.sh](gen.sh) with diycross7: MP, SB, LB,
    S, R, 2+2W, IRIW, WRC and ISA2 over the table's orderings. The writer
    side uses `str;stlr`, `dmb ishst` or `dmb ish`; the reader side uses
    `ldar`, `ldapr`, an address dependency or plain accesses. The `MPcw`
    family has CAS as the writer's release (`cas`/`casl`/`casal`); `MPcr`
    has CAS as the reader's acquire (`cas`/`casa`/`casal`).
  - 34 hand-written tests in `aarch64/hand/`:
    - the Treiber push shapes: a node initialised by `str` and linked into
      `top` by `casl`, `casal`, plain `cas`, `dmb ishst; cas` or
      `stlr; cas`. The reader loads `top` by `ldar`, `ldapr` or `ldr`, then
      the node, address-dependent (`-addr`) or not (`-po`);
    - the Treiber pop against a push (`TreiberPop+*`: `ldar`/`ldapr`/`ldr`
      of top, dependent load of `next`, `casal`);
    - failing CAS controls (`*-fail*`: a failing `casa`/`casal` still
      acquires; a failing `casl`/`casal` writes nothing and so releases
      nothing);
    - SB through CAS of each kind (diy cannot end an `Fre` at a CAS's read);
    - `ldapr` coherence (`CoRR+ldapr*`, `CoWR+stlr-ldapr`).
  - diy has no `DMB ISH`/`DMB ISHST` edges. The families are generated with
    `DMB SY`/`DMB ST` and rewritten to the inner-shareable spellings before
    herd runs (names: `dmb.sy` → `dmb.ish`, `dmb.st` → `dmb.ishst`). herd's
    `aarch64.cat` puts `DMB ISH` in the full-barrier class with `DMB SY`,
    and `DMB ISHST` with `DMB ST`. On these tests herd prints
    `Flag Assuming-common-inner-shareable-domain`, which `litmus_tests.py`
    would read as a state. `gen.sh` deletes exactly that line from the
    cached oracle; Kraken has no shareability domains, so the flag's
    assumption is Kraken's too.
- **`aarch64/lse2/`** (14 tests, hand-argued `.litmus.lse2`, run with
  `--lse2`). These are FEAT_LSE2 16-byte `ldp`/`stp` with the table's
  orderings, `casp` against `casal`, and `casp` on a 16-byte cell. Arguments
  are in its [README](aarch64/lse2/README.md). `aarch64/lse2/open/` (2
  tests, outside the regression run) holds `casp` on two 8-byte words,
  weaker than hardware ([README](aarch64/lse2/open/README.md)).
- **`x64/`** (43 tests).
  - 18 diycross7 tests (plain `mov`, `mfence`, `xchg`) and 15 hand-written
    `lock cmpxchg` tests in `x64/hand/` (SB, MP, LB, R, 2+2W, IRIW, CoRR,
    Treiber push/pop, failing `cmpxchg`), with herd oracles.
  - Kraken reads AT&T (`lock cmpxchgq %rbx,(x)`). herd 7.58's X86_64
    grammar has `cmpxchg` with the memory operand first
    (`I_CMPXCHG effaddr COMMA reg`, `lib/X86_64Parser.mly`). So `gen.sh`
    runs herd on a twin of each test with `cmpxchg`'s two operands swapped
    (same instruction: memory destination, register source, comparand in
    `rax`); the failed-`cmpxchg` study prototype did the same.
  - 11 `cmpxchg16b`/`movdqa` tests carry hand-argued `.litmus.hand` oracles
    (herd 7.58 rejects both instructions; see `../x86_64-vector/README.md`).
    They are argued below.
  - `x64/open/` (1 test, outside the regression run) is a herd unsoundness:
    see its [README](x64/open/README.md).

`gen.sh <herdtools7 bin dir>` regenerates the diycross tests and every
`.herd` oracle. It never touches `.lse2`/`.hand` files. A second run leaves
the tree unchanged.

## The x64 vector oracles

- A 16-byte value prints as one unsigned number with the low 8 bytes in the
  low 64 bits: `{1,1}` = 18446744073709551617, `{2,2}` =
  36893488147419103234.
- Atomicity, Intel SDM Vol. 3A (253668-090US):
  - §11.1.1: with AVX, the 16-byte memory operation of an aligned `MOVDQA`
    is atomic. Every location here is a 16-aligned `__int128`.
  - §11.1.2.2: `CMPXCHG16B` with `LOCK` is a locked instruction, hence
    atomic.
  - §11.2.2 / §11.2.3.9: locked instructions are not reordered with loads
    or stores, so a locked instruction is a full fence.
  - Ordering among ordinary loads and stores is TSO (§11.2.3.2–7).
  - A `movdqa` store is an ordinary write-back store, not a non-temporal
    one.

| Test | Oracle | Argument |
|---|---|---|
| `MP16+movdqa+po` | Never, 3 | `movdqa` record then flag: TSO keeps W→W and R→R. flag = 1 implies the record is `{1,1}`. Never torn. |
| `MP+po+movdqa-flag` | Never, 3 | The 16-byte record is itself the flag, after a data store. |
| `SB16+movdqas` | Sometimes, 4 | TSO lets a load pass an earlier store (to a different location): both loads may read 0. |
| `SB16+mfences` | Never, 3 | `mfence` orders W→R. |
| `CoRR16+movdqa` | Never, 6 | Two reads of one location follow coherence order `0 < {1,1} < {2,2}` (§11.2.3.7), each read whole. |
| `MP16+cmpxchg16b+movdqa` | Never, 2 | `lock cmpxchg16b (0,0)->(1,1)` vs a `movdqa` load: `0` or `{1,1}`, never torn. |
| `CAS16+cmpxchg16bs` | Never, 2 | Two `lock cmpxchg16b` from `(0,0)`: they are totally ordered (§11.2.3.8). The first succeeds; the second fails and loads the winner's record into `rdx:rax`. |
| `MP+po+cmpxchg16b` | Never, 3 | Data store, then `cmpxchg16b` as the flag. |
| `SB+cmpxchg16b+mfence` | Never, 3 | The locked `cmpxchg16b` orders its write before the later load. |
| `SB+cmpxchg16b-fail+mfence` | Never, 3 | A failing `lock cmpxchg16b` on a third location is still a locked instruction, so still a full fence. (The SDM's write-back on failure is not observable here; `../../KNOWN_GAPS.md` the failed-`cmpxchg` study.) |
| `CoWW+movdqa+cmpxchg16b` | Never, 2 | `movdqa {1,1}` vs `cmpxchg16b (0,0)->(2,2)`. Either the cmpxchg is first (succeeds, then overwritten) or it fails, reading `{1,1}` whole. The final record is `{1,1}` either way. |

## Findings about the table (all rows agree with herd/hardware unless noted)

- **`load acq` → `ldapr` is RCpc.** `stlr x; ldapr y` may be reordered
  (`SB+polqs`, `SB+po+polq`, `R+popl+polq`, `R+dmb.ishst+polq`: Sometimes),
  where `stlr x; ldar y` may not (`SB+polas`, `R+popl+pola`: Never). Store
  release then load acquire therefore gives no Dekker/SB guarantee under
  the `ldapr` lowering. On x64 neither does `mov; mov`: TSO allows SB, and
  only `mfence` or a locked instruction forbids it. `ldapr` keeps
  coherence (`CoRR+ldapr*` Never). It orders later accesses: every `MP`,
  `S`, `ISA2` and `WRC` test whose writer is ordered and whose reader is
  `poqp` is Never; the plain-writer controls `MP+po+poqp` and
  `MPcw+po-amo.cas+poqp` are Sometimes. It is multi-copy atomic
  (`IRIW+poqps` Never). herd does not allow IRIW with `ldapr`.
- **`cas acq` and `cas rel` are not full fences on AArch64.** `SB+casas`,
  `SB+casls`, `SB+cass`: Sometimes; only `SB+casals` is Never. On x64 every
  `lock cmpxchg` is a full fence (`SB+cmpxchgs`, `SB+cmpxchg-fails`: Never).
- **A failing CAS:**
  - On AArch64 a failing `casa`/`casal` still acquires
    (`MP+popl+casa-fail-po`, `LB+casa-fail-po+poap`: Never).
  - A failing `casl`/`casal` releases nothing (`MP+casl-fail+ldar`,
    `MP+casal-fail+ldar`: Sometimes).
  - A failing `casal` does not order an earlier store before a later load
    (`SB+casal-fail+dmb.ish`: Sometimes).
  - On x64 a failing `lock cmpxchg` is still a full fence.
- **Publication (Treiber push).**
  - These publish: `casl`/`casal` links, and `dmb ishst; cas`.
    `Treiber+{casl,casal,dmb.ishst-cas}+*`: Never, with any acquire reader
    or an address-dependent plain reader.
  - These do not publish:
    - a plain `cas` link (`Treiber+cas+*`: Sometimes, even against `ldar`);
    - `stlr` of the node then a plain `cas` (`Treiber+stlr-cas+ldar-addr`:
      Sometimes; the release orders what comes before the `stlr`, not the
      later link);
    - a plain independent reader (`Treiber+casl+ldr-po`: Sometimes).
  - The pop shape is safe with any of `ldar`/`ldapr`/`ldr` of top followed
    by a dependent load (`TreiberPop+*`: Never).
- **`fence st` → `dmb ishst` orders stores only.** `LB+dmb.ishst*`,
  `SB+dmb.ishst*` and `MP+dmb.ishst+po` (reader plain): Sometimes. On x64
  `fence st` lowers to nothing. TSO already orders W→W (`MP`, `S`, `WRC`,
  `ISA2` with plain `mov`: Never) but not W→R (`SB+po+mfence`: Sometimes),
  which is the same as `dmb ishst` on AArch64.
- **`casPair` → `casp*` (AArch64).** Kraken's `isa` (like herd) performs
  `CASP` as two 8-byte RMWs. The Arm ARM makes it single-copy atomic at 128
  bits.
  - On a 16-byte location (the only declaration under which LSE2 `ldp`/`stp`
    are single accesses) `isaLSE2` performs an `X`-register `CASP` as one
    16-byte RMW, so `casPair` and pair `ldp`/`stp` mix on one cell
    (`aarch64/lse2/MP+caspal-i128+ldp`, `CoWW+stp+caspal-i128`). Under `isa`
    it is unsupported, as a mixed-size access.
  - On two 8-byte words Kraken allows torn pair reads that hardware forbids:
    weaker, never stricter. See `aarch64/lse2/open/README.md`.
- **x64 `casPair`/`movdqa`.** `cmpxchg16b` and `movdqa` on one 16-byte
  location mix freely and are never torn. This matches the SDM.
- **herd x86 unsoundness** (`x64/open/R+po+poana`): herd's default
  `x86tso-mixed.cat` lets an `xchg` write coherence-before the write it read
  from. Kraken forbids it, as does the SDM. Known (`../../KNOWN_GAPS.md`,
  The failed-`cmpxchg` study).
